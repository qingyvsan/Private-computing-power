## 统一使用流程（一图看懂）

```
① 中央服务器：部署调度器（headless，仅 gRPC :9090）
② 打包分发：客户端打成压缩包发给用户（cpstart + agent + 内嵌前端）
③ 用户启动：解压 → 双击 cpstart → 自动拉起服务 → 浏览器打开控制台
④ 首次配置向导：连接调度器 / 节点身份+邀请码 / 共享资源 / 环境检测
⑤ 加入集群：节点注册上线，控制台开始操作
```

> 完整逐步说明见文末《统一使用流程（端到端）》章节。

## 三、构建

> **Windows 注意**：`make` 不可用，请直接使用下方 `go build` 命令。

### 3.1 单模块构建（go build，通用）

在项目根目录（go.work 生效）执行：

```bash
# 三个二进制输出到 bin/（cpstart 随 P3.5 交付）
go build -o bin/scheduler ./scheduler/cmd/scheduler
go build -o bin/agent      ./agent/cmd/agent
go build -o bin/cpcli      ./cli/cmd/cpcli
```

等价于在各自模块目录内构建：

```bash
cd scheduler && go build -o ../bin/scheduler ./cmd/scheduler
cd agent      && go build -o ../bin/agent      ./cmd/agent
cd cli        && go build -o ../bin/cpcli      ./cmd/cpcli
cd cli        && go build -o ../bin/cpstart    ./cmd/cpstart   # P3.5 一键启动器
```

### 3.2 Makefile（Linux/macOS）

## 四、运行

### 4.1 一键启动（cpstart，用户主机使用）

> 运行在**用户自己的电脑**上（调度器部署在服务器，无界面）。下载一个可执行文件，双击即用，浏览器自动打开本地控制台。

```bash
# Windows：解压后双击 cpstart.exe
# Linux/macOS：./cpstart
```

启动器自动完成：
1. 拉起本机 Agent，注册到远程调度器（默认 `8.138.108.183:9090`，可在配置中改为其他地址）
2. 启动本地控制台（Web UI + REST 桥接，仅监听 `127.0.0.1:8080`，不出网）
3. 打开默认浏览器进入 `http://127.0.0.1:8080`
4. 在界面中操作：节点 / 作业 / 信任图 / 邀请码（数据经远程调度器）
5. Ctrl+C 优雅退出，数据保存在本地

无需安装任何依赖（Go 单二进制 + `go:embed` 内嵌前端）。中央调度器保持 headless，仅提供 gRPC。

### 4.2 启动调度器

```bash
# 方式一：go run（开发）
cd scheduler
go run ./cmd/scheduler --config ./configs/scheduler.yaml

# 方式二：二进制（部署）
./bin/scheduler --config ./scheduler/configs/scheduler.yaml
```

调度器为无界面后端（headless），默认监听：
- gRPC：`0.0.0.0:9090`
- HTTP 健康检查：`0.0.0.0:8080`（配置中默认 `enabled: false`，仅探活，不托管页面）
- Sync 服务（P8 Primary 模式）：`0.0.0.0:9091`

数据落盘：`scheduler/data/scheduler.db`（BoltDB，自动创建目录）

**P8 热备模式**（`sync.enabled: true`）：
- **Primary 节点**：正常启动，额外监听 `:9091` 提供 WAL 同步服务，自动创建检查点
- **Standby 节点**：不启动 gRPC server，连接 Primary 的 `:9091` 实时同步 WAL 数据；当 Primary 宕机超过 15s 后自动提升为 Active，启动 gRPC server :9090 接管服务

```bash
# Primary 启动（默认）
./bin/scheduler --config ./configs/scheduler.yaml
# 日志: wal enabled, sync service listening on 0.0.0.0:9091

# Standby 启动（sync.role: standby, sync.primary_addr: 8.138.108.183:9091）
./bin/scheduler --config ./configs/scheduler-standby.yaml
# 日志: standby mode: syncing from primary, promoted to active (failover)
```

> 注意：配置文件中的相对路径（`./data/scheduler.db`、`./configs/ca.pem`）相对于**运行时的当前工作目录**。

### 4.3 启动 Agent

```bash
# 方式一：go run（开发）
cd agent
go run ./cmd/agent --config ./configs/agent.yaml

# 方式二：二进制（部署）
./bin/agent --config ./agent/configs/agent.yaml
```

Agent 启动后：
1. 连接调度器（默认 `8.138.108.183:9090`）
2. 注册节点（自动生成 `node-<时间戳>-<name>`）
3. 建立双向流心跳（默认 3s 间隔 + 0.5s jitter）
4. 断线自动重连（1s → 60s 指数退避）

### 4.4 停止服务

```bash
# Ctrl+C 优雅退出（scheduler 收到 SIGINT/SIGTERM）
# 异常清理测试进程
taskkill //F //PID <进程PID>      # Windows
kill <进程PID>                    # Linux
```

## 六、作业 YAML 规范

### 单体作业（job-single.yaml）

```yaml
name: "my-inference-service"
type: single                        # single | aggregate | workflow
image: "user/llm-server:v1"
resources:
  cpu: 4
  memory: 16GB
  gpu: 8GB
strategy: long_running
failure_policy: auto_retry
```

### 工作流作业（job-workflow.yaml）

```yaml
name: "ml-training-pipeline"
type: workflow
owner_id: "node-user-1"
max_retries: 3
stages:
  - name: download
    image: "user/data-fetcher:v1"
    resources: { cpu: 1, memory: 2GB }
    outputs: ["/data/raw"]

  - name: preprocess
    image: "user/preprocessor:v1"
    depends_on: ["download"]
    split:
      strategy: by_file          # by_file | by_range | by_n | by_custom
      input: "/data/raw/*.csv"
    resources: { cpu: 2, memory: 4GB }
    outputs: ["/data/processed"]
    max_concurrency: 10

  - name: train
    image: "user/trainer:v1"
    depends_on: ["preprocess"]
    resources: { cpu: 8, memory: 16GB, gpu: 8GB }
    max_concurrency: 1
```

资源单位：`memory` 支持 KB/MB/GB/TB；`gpu` 用 GB 表示显存请求。

## 九、常见问题排查

| 现象 | 原因 | 处理 |
|------|------|------|
| `make` 命令不存在 | Windows 无 make | 使用 `go build` 直接构建 |
| BoltDB 打开失败 / 锁占用 | scheduler 残留进程 | `taskkill //F //PID <pid>`，删除 `scheduler/data` 后重启 |
| 序列化错误 `want proto.Message` | codec 未生效 | 确认 scheduler 用 `ForceServerCodecV2`、client/agent 用 `ForceCodecV2` |
| Agent 注册失败 | 调度器未启动 / 端口不通 | 检查 9090 端口，先启动 scheduler |
| 配置找不到 | 相对路径基于 CWD | 在对应模块目录下运行，或用绝对路径 |
| 节点一直显示 offline | φ 检测生效，心跳中断 | 检查 Agent 进程与网络，等待重连 |
| 双击 cpstart 未打开浏览器 | 端口占用 / 首次启动较慢 | 检查 8080/9090 端口，或手动访问 http://127.0.0.1:8080 |
| 界面看不到节点/作业 | cpstart 未连上远程调度器 | 检查 cpstart 配置中的 scheduler 地址及 9090 连通性 |
| Standby 无法连接 Primary | sync.primary_addr 配置错误 / 防火墙拦截 :9091 | 检查 Primary 是否启用 sync，telnet 测试 9091 端口连通性 |
| Standby 一直不提升 | 健康检查未超时 / Primary 仍存活 | 检查 `health_check_interval` 和 `failover_timeout` 配置，确认 Primary 进程已停止 |
| WAL 同步失败 | 序列号不连续 / BoltDB 快照不一致 | 检查 `data/wal/` 目录日志文件，删除 WAL 目录后重启 Standby 全量同步 |

## 十、部署拓扑（目标形态）

```
                 ┌─────────────────────────────┐
                 │ 调度器 Primary（服务器，无界面）│   gRPC :9090
                 │  + Sync :9091               │   HTTP :8080 (仅健康检查)
                 │  + BoltDB + WAL             │
                 │  + Nebula Lighthouse :4242   │   UDP :4242 (Nebula)
                 │  + CA 证书签发              │
                 └───────┬─────────────────────┘
                         │ gRPC Sync (WAL 流复制)
                 ┌───────▼─────────────────────┐
                 │ 调度器 Standby（备节点）       │   gRPC :9090 (故障后接管)
                 │  + Sync Client               │   Sync :9091 → Primary
                 │  + BoltDB + WAL (回放)        │
                 │  + 健康检查 (5s)              │
                 │  + 自动提升 (15s 超时)         │
                 └─────────────────────────────┘
                         │ gRPC + 心跳 + Nebula overlay
          ┌──────────────┼────────────────────────────┐
          │              │                            │
   ┌──────▼─────┐  ┌─────▼──────┐  ┌───────────────┐  │
   │ 用户主机 A  │  │ 用户主机 B  │  │ 纯算力节点    │  │
   │ Agent+Nebula│  │ Agent+Nebula│  │ Agent+Nebula  │  │
   │ 浏览器→:8080│  │            │  │               │  │
   └──────┬─────┘  └─────┬──────┘  └───────┬───────┘  │
          │              │                │           │
          └──────── Nebula Overlay 网段 ───┘           │
                  10.1.0.0/16 + Lighthouse 10.0.0.1   │
                  节点间直接 P2P 通信（穿透 NAT）       │
```

P8 热备故障切换流程：
1. Primary 正常运行，Standby 通过 SyncWAL 流实时拉取 WAL 增量
2. Standby 每 5s 健康检查 Primary，连续 3 次失败（15s）触发切换
3. Standby 停止同步，提升为 Active，启动 gRPC server :9090
4. Agent 断线重连机制自动连接到 Standby
5. RPO ≤ 5s（WAL 同步延迟），RTO ≤ 30s（含 Agent 重连）
